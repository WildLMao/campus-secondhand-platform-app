# D · 业务审查与独立验收

先读[共同协作约定](../协作约定.md)和[协作包入口](../../README.md)。本 skill 中的源码、配置及新增 `docs/` 路径均相对包内 `reference-app/`；需求编号以包内 `requirements/documents/软件工程课程需求报告.md` 为准。目标是用可重复的输入、响应和数据结果判断实现是否符合正式需求，并将缺陷交原负责人修复。以原反例复验关闭问题，不以口头说明或页面看起来正确代替结论。

## 输入与审查范围

读取正式需求 FR01—24、UC01—12、BR01—20、物品和订单状态 ST、AC-D-01—12，结合质量报告了解历史结论范围。获取 A 的部署版本和环境、B 的接口/数据库版本及测试结果、C 的页面入口和走查结果。

先建立或更新项目 `docs/verification/` 下的需求覆盖、验收场景与问题台账。已有编号沿用；新增实现问题用 DEV-D 编号，历史需求 V 号作为关联，不覆盖旧证据。

## 关键检查矩阵

| 方向 | 需要构造的反例和结果检查 |
| --- | --- |
| 准入与发布 | 未认证发布/下单、认证退回重提、旧版本审核、占用中修改/撤下；失败不改变现有事实 |
| 身份与归属 | 第三人订单/会话/回执、买卖职责交换、管理员代收货、身份材料和图片越权；分别检查 API 与页面 |
| 唯一下单 | 两个买方同时下单，最多一笔有效订单；失败无孤立订单、快照或占用 |
| 重复意图 | 同意图并发、成功后响应丢失、终态后重试、后续账户受限、同标识改内容；校验原回执及归属 |
| 交付与取消 | 未登记收货、已登记取消、无未交付声明、报告已交付、取消与登记同时到达；最多一个相容结果 |
| 受限与隐藏 | 禁止新业务，保留本人旧单查询、允许的履约与维权；取消、解封、解除隐藏都不能绕过其他限制 |
| 争议 | 三个未结束阶段分别受理与继续履约；保留原阶段和占用，暂停接单/拒单/登记；已登记时买方仍可确认 |
| 异常终止 | 须有核查依据，不能仅因沉默；无登记时不能补造交付；释放占用但不可自动重售，核实后重发重审 |
| 历史与反馈 | 快照不随物品修改，终态消息只读，终态举报不重开、不占用、不改成交；重复评价不追加 |
| 统计与通知 | 只有买方确认完成计成交，按快照金额去重；时间边界一致；通知失败不能回滚已成立业务 |

P2 仍在本期范围，不能因首版未覆盖就默认为删除。认证、发布、搜索、收藏、消息、评价、举报和统计也要有明确验收入口，不能只测核心订单。

## 怎么执行才算验证

1. 每个场景记录需求/规则编号、输入版本、环境、测试数据、执行身份、具体接口或页面步骤、预期和实际结果。
2. 正常流程使用真实前端与接口；越权、篡改和竞争可直接调用测试环境接口。使用独立用户会话，不能用页面模拟角色切换证明权限隔离。
3. 并发使用独立请求/连接及同步发起机制，记录各响应与最终数据；顺序请求只算先后顺序测试。需要准确调度竞争时与 B 约定测试设施，说明其与真实请求的差别。
4. 同时核对响应和数据库业务不变量：有效订单数量、唯一占用对应关系、物品/订单状态、快照、交付、回执、统计及必要操作记录。业务拒绝不应留下部分写入。
5. 响应丢失与通知失败可用受控测试设施复现，明确故障注入点；测试设施不暴露到正式公网。没有接入的通知渠道不虚构投递测试。
6. 本地 H2、真实 MySQL、公网浏览器、持久挂载及恢复分别记录结果。与 A 共同核验域名、HTTPS、完整请求及恢复；D 不接管日常服务器运维。

## 问题分派与复验

每条问题至少记录：DEV-D 编号、关联 FR/BR/ST、严重性、前置数据、完整操作、预期、实际、证据位置、影响、负责人、修复版本、复验结果。必须修改的问题与完善建议分开；不因建议未采纳阻塞已满足需求的交付。

- 公网入口、DNS、证书、挂载、运行与恢复问题交 A。
- 数据库、接口、权限、事务与规则实现问题交 B。
- 页面入口、按钮、校验、提示、布局及会话展示问题交 C。
- 需求歧义由 D 列出原文与备选解释，组织成员/用户决定并记录；不能擅自改规则让现有程序通过。

D 维护独立场景、测试和问题台账，默认不替 A/B/C 大范围重写产品代码。原负责人修复并自测后，D 用相同反例复验，再检查受影响的关键路径。收到明确跨模块修复任务时可修改相应代码，但交接中区分修复者与独立复验者。

## 交付与接受条件

交付需求覆盖关系、实际执行记录、开放问题和复验闭环；记录访问入口、代码/数据库版本与执行环境。结论按场景给出通过、失败或未执行及其限制，不能只报一个通过数量。

阶段接受应说明已通过范围、阻塞问题、可后续处理建议和未执行项目。核心交易不变量、权限、数据持久化或公网关键路径仍失败时，不声称整体验收通过；阶段停止不等于自动关闭问题。
