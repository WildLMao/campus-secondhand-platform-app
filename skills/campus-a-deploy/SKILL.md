# A · 服务器与公网交付

先读[共同协作约定](../协作约定.md)和[协作包入口](../../README.md)。本 skill 中的源码、配置及新增 `docs/` 路径均相对包内 `reference-app/`；需求编号以包内 `requirements/documents/软件工程课程需求报告.md` 为准。目标是交付一个公网可用、数据持久、能更新和恢复的运行环境。DNS 解析成功或容器启动不能单独算完成。

## 输入与起点

读取项目 `Dockerfile`、`compose.yml`、`.env.example`、构建启动脚本；获取 B 的数据库连接约定、初始化方法和 C 的构建入口。确认服务器系统、CPU/内存、磁盘、目标端口、域名控制权及 DNS 服务方。

已有 Compose 包含 MySQL 和应用，应用映射到宿主 `127.0.0.1:18080`，MySQL 未公开映射；保留数据库不对公网开放的边界。检查应用容器内监听地址与反向代理拓扑，不能把容器回环地址误当宿主地址。

## 负责的工作

1. 在指定服务器准备运行环境与持久目录，确定 Compose 的项目名、数据卷和部署文件位置。
2. 与 B 联调 MySQL 启动、健康检查和应用连接；增加合理的重启策略、日志轮转及资源配置，按实际内存测量调整。
3. 持久化数据库和上传文件。数据库健康不代表上传目录可写，分别验证权限、重启和重新创建容器后的读写。
4. 将指定域名解析到公网入口，核对 A/AAAA 等实际记录；不保留指向错误地址的记录，不改动无关邮件或其他业务解析。
5. 配置反向代理与 HTTPS，明确只暴露网站及受限运维入口。对齐应用的代理头、Cookie 安全属性、上传体积限制与实际访问域名。
6. 使用 B 提供的正式管理员初始化流程，确认公网交付不开放演示账号；A 不直接绕过密码存储机制改写数据库密码。
7. 建立数据库与上传文件的备份方式、存放位置和恢复步骤；在独立测试库/目录完成一次恢复，不用覆盖唯一运行数据来证明恢复。
8. 记录更新步骤和回退方式。应用镜像、数据库结构和文件版本有关联，不能只回退镜像就声称数据也已恢复。

## 挂载与公网验收

为测试使用明确标识的账户和物品，保留测试记录；不删除真实数据来重置环境。

| 验证 | 必须观察的结果 |
| --- | --- |
| 外部网络访问 | 从服务器以外的网络通过域名打开网站，HTTPS 正常；不能只在服务器 curl localhost |
| 完整请求 | 注册/登录、物品检索、图片上传与读取、一次授权业务写入均正常 |
| 应用重启 | 已提交数据与上传图片仍在；内存 Session 失效需重新登录属于当前预期 |
| 容器重新创建 | 保留卷重新创建容器后，数据库记录及其图片关联仍可读；不执行删除数据卷的命令 |
| 服务器重启 | 按实际约定自动恢复服务，域名入口恢复，数据仍在 |
| 备份恢复 | 恢复到独立目标后核对账户、订单、快照、占用和图片，记录恢复耗时及差异 |

## 边界与交接

A 维护部署配置和运行环境；数据库表、迁移脚本、后端规则问题交 B，页面和构建行为问题交 C，业务争议交 D。需要跨文件调整时说明原因及影响，不自行改变交易规则。

交付可直接执行的部署、更新、停止、恢复步骤及必要配置模板；模板不含真实秘密。向 D 提供域名、部署代码/镜像版本、环境说明、上述实际结果及证据位置。缺少服务器、DNS 或证书所需条件时，报告具体缺项，不虚构公网验证，也不自行购买资源。

完成条件：D 能从独立网络按域名访问，按交接复核挂载和恢复；尚未验证的重启或恢复项明确保留，不写成全部完成。
