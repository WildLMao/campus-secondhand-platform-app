## 协作模式

采用“同一仓库、成员任务分支、PR审阅后合入main”的方式。`main` 保存小组已接受的共同版本，成员在各自分支修改；实际使用过的分支包括 `a/business-v2`、`b`、`feat/C` 和 `d/verification`。

1. **开始任务**：保存本地修改，同步最新共同版本，读取共同大纲、协作协议、本人角色 skill 及上轮交接材料。
2. **完成一批成果**：在任务分支修改本人负责的内容，检查规则、编号、图源与导出文件是否对应，整理交接证据。
3. **发起PR**：说明本次完成内容、修改位置、检查结果和影响范围，申请合入 `main`。
4. **审阅与修订**：D分批核验A/B/C成果，在PR中提出问题或完善建议；原作者在同一PR分支继续提交修订，便于对照复核。D本人的成果由其他成员按负责范围交叉复核。
5. **接受与合并**：审阅后决定接受、继续修改或保留问题。建议与错误分别记录；阶段接受不自动关闭仍需处理的问题。
6. **向下游交接**：合并后，后续成员同步最新 `main`，再继续编辑；网页合并不会自动更新各人的本地文件。

实际提交、审阅、回复及合并记录见[E-D-12 GitHub协作记录](attachments/evidence/GitHub协作记录.md)。

## 文档维护与核验约定

* **同步正文与导出**：三份报告的 Markdown、Word、PDF均在 `documents`。修改后同步对应格式；转换工具不限，以内容一致、图表清晰及格式正确为准。Word批注稿先保留，再处理修订并核对各版本。
* **维护原作者内容**：业务规则、模型及原型的实质修改交回对应负责人；全文格式统一按共同规范及A版样式执行，涵盖封面、目录、标题、表格与居中表题。
* **沿用统一编号**：FR为功能需求、UC为用例、BR为业务规则、ST为状态转换、SC为场景、PV为原型验证、V为问题、E为证据。同一项内容跨文档引用时沿用原编号，修改模型时同步图源、导出图、说明及转换表。
* **按实际范围记录结果**：本包原型为页面与内存规则模拟，运行方式见[原型说明](attachments/prototype/README.md)。资料核对、AI自动检查、人工走查和后台功能验证分别记录；问题是否关闭以修改位置及复核证据为准。
