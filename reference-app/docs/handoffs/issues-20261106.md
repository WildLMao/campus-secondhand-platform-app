## 2. 有边界的自查

自查范围：同类公开接口投影/治理字段泄露、收藏与私有上下文权限、注册前端是否 trim、消息 readonly 实际模板。结果（未新增需求、不编造额外 bug）：

- **公开接口**：`GET /api/items` 已改为字段投影。`/api/sellers/{id}/reviews`、`/api/health`、`/api/me` 无治理字段或已按字段返回；`/api/admin/**` 仅管理员（`admin(uid)` 前置）。
- **公开联系方式（主审确认，见 §1 末行补充修复）**：首轮自查把公开物品校验为“字段投影”，**漏掉了字段内容中的联系方式**；主审 `privacy-probe.cjs` 以真实 HTTP 确认 `confirmed_public_contact_leak:true`（审核后的 `description` 原样返回 `13800138000`/`test@example.com`）。已按 BR14 以既有 `ImageGuard.mask` 在读取时处理 `title`/`description`/`seller_name` 与可用收藏 `title`，历史数据同样受保护，原文与价格/ID 不变，正常型号不误伤。主观层面的漏检已作为本轮自查结论记录。
- **收藏/私有上下文**：`favorites`、`mine`、`messages/context`、`orders`（含 `/details`）均按本人或当事人校验；管理员不自动获得订单私聊（既有用例 `adminDetailsThroughDisputeAndMessageAccessStaysScoped` 覆盖）。
- **注册前端**：`App.vue` 注册/登录共用一个 `<form>` 与 `authenticate()`，`body={...login}` 原样提交，无 `trim()`；仅新增一句注册说明（“密码按原文保存，首尾空格也算密码的一部分；至少 8 个字符且不超过 72 字节”）。后端 `minlength=8`/`maxlength=72` 与新规则一致（72 为字符数上限，字节上限由后端明确拒绝）。
- **消息 readonly 实际模板**：模板为 `v-if="chatState.value.readOnly"` 只读提示 / `v-else` 的 `search chat-compose` textarea（`@keydown.enter="onEnter"`），`readOnly=data.readOnly!==false` 只认服务端字段；本轮未改模板，只在既有行为测试中补充断言：读取与发送使用同一 `chatQuery(c)`，前端不把本人 uid 当咨询人参数。
- **自查中撤回的改动**：曾试加“ITEM 咨询读取时按公开评价规则脱敏联系方式”，经主审判定该行为超出 4 个 Issue 且私聊不构成公开泄露，已完整撤回（`messageList` 恢复为原样返回，相关断言/文档说法删除）。**即时消息内容保持原文，公开评价既有脱敏（`reviews()` 读取时 `images.mask`）不变。**
- **额外新增（与 #15 同因，属既有契约）**：非卖方读取路径不依赖 `peer` 后，`GET/POST /api/messages` 的买方不再需要传本人 uid；这是修复 #15 所必需的参数归一化，不改变任何权限，已写入 API 文档。
